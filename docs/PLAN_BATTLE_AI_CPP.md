# PLAN_BATTLE_AI_CPP.md — порт боевой логики и поиска пути в C++ модуль

## Цель

В `ldhook.pyd` должна быть читаемая реализация боевой логики и поиска пути по
слоям:

```
FUN_0044bdd0  тик боевого AI (верхний уровень)
└── FUN_0045eee0  движение/выбор точки
    └── FUN_0045e0a0  поиск цели
        └── FUN_0045dd70 / FUN_0045cb40  pathfinding
```

Код модуля — источник истины об алгоритме: имена структур, полей и функций
отражают смысл, а не адреса. Конечный артефакт понимания — `docs/OBSERVATIONS_BATTLE_AI.md`
(Фаза 6) плюс сам C++.

Оптимизация производительности **не цель**. Обязательное условие — эквивалентность
поведения оригиналу (fidelity-first); CPU боя остаётся как у baseline.

## Границы порта

**Портируется** — всё, что принимает решения: выбор цели, обновление метрик и
фронта, стоимость и обход пути, состояние боевого AI, таймауты, учёт занятости
клеток (на уровне «какие решения принимаются»).

**Не портируется**, вызывается нативно через именованные обёртки `native::…`:

| что | почему |
|---|---|
| GUI/HUD/анимация/отрисовка, строки, форматирование, логирование движка | не часть алгоритма |
| `0x442570` (состояние игры: внутри строки и vtable-вызовы) | не часть алгоритма |
| аллокатор `0x47abc0` и вставки в родные `std::map` (`0x45d2e0`, `0x45d810`, `0x45dd00`) | runtime-плумбинг; второй аллокатор = порча кучи (дефект C прошлой сессии) |
| загрузка ассетов/материалов/текстур | не часть алгоритма |

Правило классификации: функция портируется, если она (а) меняет выбор цели,
(б) считает/меняет стоимость пути, (в) меняет состояние боевого AI. Иначе —
нативная обёртка с именем по смыслу. Спорные функции разбираются в п. 1.4, решение
фиксируется в `docs/OBSERVATIONS_BATTLE_AI.md`.

Следствие: RB-вставка в `std::map` (бывшая Фаза B старого плана) **не портируется**;
порт `0x434bc0` (lower_bound) и `0x47f800` (next) остаётся — он уже сверен и не
аллоцирует.

## Инварианты

1. Игра только для чтения; установка — `exepatch12` (`171319bb…`), эксперименты —
   baseline scratch (`45e93d46…`), запись в установку — только явным `--install`.
2. `/fp:precise` обязателен; последовательности x87 переносятся 1:1 (см. 1.6).
3. Все игровые адреса — через `native::fn(VA)` (база модуля + смещение от 0x400000),
   без «голых» VA в логике.
4. Дизасм-гейт: ни одна функция не портируется без строки дизасма в артефакте
   разведки (Фаза 1).
5. Один детур на функцию; портированный слой вызывает порты напрямую, нативные
   обёртки — только для листьев.
6. Каждый пункт плана = отдельный коммит (≤2 строки) + обновление статуса здесь.

## Исполнение

Оркестратор (текущий агент) запускает **последовательных** сабагентов по одному пункту.
Модель сабагента выбирает оркестратор. **Всё, кроме среднего и сложного, — `strata/q3.8-fn#medium`**;
**ревью любого пункта — `strata/q3.8-fn#high`**.
Средние и сложные — `openrouter/particle-ai/particle-1:free#high`: при обрыве до
10 раз продолжаем той же сессией командой `continue`; после 10-й неудачи — эскалация к
человеку (если человек не указал иное). Замер контекста сессии (`<scratch>/ctx.py`) —
только при отправке нового задания: при ≥256k задание не ставить, открывать новую сессию;
при `continue` замер не нужен.
Если человек сообщает, что суточные лимиты бесплатных моделей исчерпаны, средние и
сложные идут на `openrouter/@preset/ds-flash-41-cheapest#low`. «Перевод» живой сессии на
другую модель — сменой модели сессии через API opencode
(`opencode api post /api/session/<ses>/model`), не новой сессией.
Пока particle работает плохо (23.11.2026): **5 ошибок подряд** в живой сессии → перевод на
`openrouter/baidu/ernie-5.5-flash-preview:free#high`; новые средние/сложные — сразу на particle.
После отката суточных лимитов (03:10 по местному) реализация снова идёт на particle; до этого
времени — разведка и ревью на strata, старт порта откладывается до отката.
Параллельные запуски запрещены.
Простая рутина (разведка по листингу, таблицы, ABI-сверки, длинные docs-заготовки) — тоже
strata; коммит и финальная правка docs — оркестратор.
Неразрешённая семантика (callee, структуры, ABI) — сначала REA (decompile/xrefs), затем
листинг; догадки по asm запрещены.

Пункт передаётся с входами, выходом и гейтом; без пройденного гейта следующий пункт
не стартует. Исследовательские пункты пишут артефакт в `<scratch>/re/…`
(`<scratch>` = `config[scratch.dir]`), в docs попадает только принятое решение.
Предыдущие артефакты дизасма (`battle_ai_disasm{,2}.md`, `battle_ai_structs.md`,
`site6_audit.md`, `metric_semantics.md`) — рабочий scratch прошлой сессии, в git
не входят.

### Конвейер пункта

1. **Исполнитель** — реализует пункт по дизасму.
2. **Рецензент** (отдельный сабагент) — сверяет дифф с планом и дизасмом: fidelity,
   ABI, аллокатор, рекурсия, гонки, читаемость имён. Вердикт: pass / minor / major / critical.
   - major или critical → отдельный сабагент-исполнитель устраняет замечания, затем
     снова рецензия (шаг 2).
   - minor — фиксируется в отчёте, не блокирует.
3. **Тестировщик** (отдельный сабагент; только для пунктов, где C++ должен быть
   работоспособным) — прогон «Боевого гейта», см. ниже.
   - тест не прошёл → до **3** попыток исправления (каждая — отдельный сабагент-исполнитель) и повторный тест;
   - после 3-го провала → **эскалация на человека**: оркестратор останавливает цепочку и приносит отчёт (шаг, дифф, лог, снимок).
4. **Оркестратор** — коммит, обновление статуса здесь и в `docs/STATE.md`.

### Боевой гейт (снимок саммонов)

`tools/probes/battle_169.ps1` (обёртка `perform_action_in_game.ps1`, аргументы захардкожены)
на установке (`config[game.root]`, `3840x2160`; A/B на scratch — `LDHOOK_LOG=1`).
Сценарий: вход в бой по фиксированным шагам → 3 волны призыва (каст по земле, `-Waves 3`) →
**снимок через 1 с после 3-й волны** → игра гасится.

Критерий: на снимке рядом с персонажем **≥2 призванных саммона**. Точка спавна фиксирована
(`FIXED_ENTRANCE_INDEX = 5`, `patches/bdomain.py`; `docs/PATCHES.md`), дистанция до ближайшего врага
постоянна, персонаж не ходит; проверяются наличие саммонов и отсутствие визуальных поломок.
Курсор в бою не подводить к краю экрана (камера).
Эталон процедуры — `scratch_dir('battle_baseline')/baseline_summons.png`.

1.6. **x87-точность.** Решить, как переносить `c690`/`c5e0`/`c3a0`: MSVC x86 `/fp:precise`

   `__asm`-блоки только в этих трёх функциях; (б) double + эмпирическая проверка
   границ. Решение фиксируется здесь до Фазы 2.

   **Решение 1.6.** Control word игры — PC=53 (double) везде: все 32 sites `fldcw` —
   только CRT-math, `_controlfp` не импортируется и не вызывается, поэтому plain double
   в MSVC `/fp:precise` бит-эквивалентен comparison-гейтам. Правила ветвлений (проверено
   probe): JP(маска 0x5) ⟺ NOT(a<b); JNZ(0x41) ⟺ NOT(a>b); JP(0x44) ⟺ (a≠b, unordered
   считается «не равно»). Метод по местам: `45c5a0`, `45c3a0`, `45cb40` (гейт), `45c5e0`,
   `456b20`, `45c570` → plain double; границы `45cb40` (`0x45cc4d..0x45cc6f`) →
   целочисленные сравнения; `45c8c0` → asm bridge для FPTAN (`0x45c94a`) — единственное
   не-double место; x87-гейты внутри диапазонов `44bdd0` → dual: native-вызов возвращает
   double, гейт по таблице правил. Pitfall: не грузить reset-слово `0x0040` (снятие масок
   включает x87 traps); при пиннинге PC — только `saved & ~0x300` из сохранённого слова.
1.7. **Методика эквивалентности.** Определить, что сравниваем native vs порт:
   последовательность тиков, id цели, координаты точки движения, значения `g/h/cost`,
   число посещённых узлов. Зафиксировать поля trace-строки (6.2) и способ A/B на

   Цели: переиспользование `PathState`, отсев по `map2`, стоимость рекурсии `45c3a0`.
   **Нужен, если 9.1c не удержит темп:** при потолке итераций цена пути становится
   основной статьёй каждого оставшегося шага.
   **9.3 (27.11.2026):** порт `e0a0` — дефолт 1 (`LDHOOK_SITE6=0` откат), тик `45eee0` — дефолт 0;
   синтетика 13 юнитов даёт `e0us/us` = 72.6 % тика. Замер настоящего боя: `LDHOOK_BATTLE_TRACE=2`
   (`TICKSEC`: тиков/с, занятость AI, `>20 ms`, `e0_sum`) + `tools/probes/tick_stats.py`;
   цель — решить по `TICKSEC`, где лаг: доля `e0a0` в тике или сам тик при 40+ юнитах.
   **9.2a принято (27.11.2026):** path-слой = 80–90 % µs `e0a0` (window-цикл+гейты 53 %, `map2`
   `lower_bound` 23 %, grid-lookup 10 %, `45c3a0` 13 %); **ни мемоизация `(cell,target)` (повторы
   2.7–9 %, все внутри одного вызова), ни per-tick бюджет (тик >50 ms = 0) не levers — цель:
   удешевить window-цикл; следующий замер — доля ячеек окна, отсеиваемых проверкой расстояния.**
   Реализация: `battle/path.cpp` (`s6_path_search`, таблица повторов), env `LDHOOK_E0_DIAG=1`.
   µs диага — верхняя граница (QPC-пара на итерацию): грабля — `docs/PITFALLS.md`.
9.3. Порт `45c8c0` (радиусы/RECT/порог из вьюпорта → мировое окно) — только если
   9.d3 не закрывает (3) и (2); это же объясняет «агро в большом радиусе» и
   «юнит не видит врага рядом»: окно поиска экранное.

Гейт фазы 9: 9.d1 rc 0 на живом прогоне + `battle_169.ps1` (≥2 саммона) +

«стоит на месте» (сценарий скрипта его не гарантирует).

## Слишком большое / малоизученное (решается разведкой)

1. **1.3b `44bdd0`** — ~1400 строк asm, SEH, x87. Одним пунктом не делать: сначала
   1.3a, затем N блоков. Оценка объёма — только после 1.3a.
2. **1.2 `45eee0`** — дизасма нет; «~120 строк» — оценка по frida, реальный размер
   неизвестен (call sites `0x45f264/0x45f368` и хвост `0x45f3a5` намекают на
   большее). Если >600 байт — дробить по блокам.
3. **1.0 раскладка `BattleAI`** — **снято (Фаза 1)**: противоречие сведено, раскладка —
   `battle/structs.h`.
4. **1.4 инвентарь листьев** — зависит от 1.3a; объём GUI/строк неизвестен, пока
   не размечен. Это же определяет, сколько в `44bdd0` реально «алгоритма».
5. **1.6 x87** — снято решением 1.6 (plain double; `asm`-bridge только для FPTAN).
6. **1.7 методика A/B** — снято: гейты Фаз 3–5 — офлайн replay (решение 3.7);
   живой A/B — санитарный, `trace_diff.py` — наблюдение.
7. **Фаза 5 целиком** — оценка невозможна до 1.3a/1.4; вероятно 6–10 пунктов.
8. **GUI внутри `44bdd0`** — если GUI-вызовы перемешаны с логикой в одном блоке,
   сохранять порядок side effects придётся вручную; риск визуальных регрессий.

## Риски

- Куча: весь путь аллокации — только игровые функции; `malloc` из `.pyd` запрещён.
- Рекурсия: `dd70` → `dd70`, `44bdd0` → `45eee0`; глубина и защита — по дизасму.
- Виртуальные вызовы: если `44bdd0`/`45eee0` вызываются через vtable, порт должен
  сохранить диспетчеризацию.
- Поведение игры зависит от кадров (frame-rate-адаптивность подтверждена), точка спавна фиксирована
  (`FIXED_ENTRANCE_INDEX`, `patches/bdomain.py`) и дистанция до врага постоянна: A/B — на одном сейве
  и сценарии, сравнивается trace решений; снимки одного индекса совпадают попиксельно.
