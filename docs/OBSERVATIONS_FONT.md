## Шрифт: контрольный замер 1280x960 и природа масштаба текста (2026-11-14)
- `[P]` **Контрольный ориентир снят.** Режим `1280 960 32 0` (окно; `k = 960*1024/(1280*768) = 1.0`,
  все обёртки `hd_scale` = identity). Клик по глифу «Изменить» (`COORDS_MM_Options=[611,532,128,256]`,
  канвасный центр (675,660) → экран (843.75, 825)) открывает `bpref.ShowPref()` =
  `gui_templates.pref_dlg` (`pd_dlg_width=960`, `pd_dlg_height=720`, `BGCS_VCENTER/HCENTER`
  → канвасный origin (32,24)). Снимки: `scratch_dir('ld')/ref1280_hover.png` (снимок прогона),
  `scratch_dir('ld')/ref1280_dialog.png` (снимок прогона),
  `scratch_dir('ld')/ref1280_dialog_nocursor.png` (снимок прогона) (1280x960). Игра в этом режиме показывает список
  разрешений 640x480 / 800x600 / 1024x768 / 1280x960 — 1280x960 действительно максимум.
- `[P]` Пересчёт канвас→экран для наведения/клика (выведен, подтверждён в обоих режимах):
  `экран_x = (h/768)*Cx + DX*(w/1024)`, `экран_y = (h/768)*Cy`; `k = h*1024/(w*768)`, `DX = 512*(1-k)`.
  Окно (F=0): квант X = `w/1024`, квант Y = 1; fullscreen (F=1): квант = `w/1024`, `EY = k*y`
  → экран `s*k*y = (h/768)*y`. Скрипт: `tools/archive/probes/probe_dlgshot.ps1` (пишет `hd.cfg`, наводит OS-курсор,
  кликает ЛКМ, снимает ТОЛЬКО окно).
- `[P]` Замеры текста (`tools/archive/probes/measure_textrows.ps1` — построчный профиль яркости, порог 170):

  | режим | s = w/1024 | k | аргумент `SetFont` (Size=12) | полоса глифов заголовка, px | rect заголовка (канвас 24) на экране, px | доля текста в rect |
  |---|---|---|---|---|---|---|
  | 1280x960 окно | 1.25 | 1.0 | 12 | 17 | 30 | 0.567 |
  | 3840x2161 F=1 | 3.75 | 0.7504 | 9 | 54 | 67.5 | 0.800 |

  В 16:9 текст относительно интерфейса крупнее в **1.41×** (расчётное `1/k = 1.333` + шум полос).
- `[P]` **Аргумент `SetFont(font, size)` движок игнорирует.** Эксперимент в 4K: `SetFont(fnt, Size*k*2)`
  (`HD_FM=2`) → снимок `scratch_dir('ld')/dlg4k_fm2_dialog_nocursor.png` (снимок прогона) визуально совпадает с
  `scratch_dir('ld')/dlg4k_dialog_nocursor.png` (снимок прогона), полоса глифов 54 = 54. Текст рисуется **битмап-глифом фиксированной
  высоты ≈ 14.4 движковых px**, масштабируется только общим `s = w/1024`.
  Шрифты: `ld_uncial12.btf` = лист 256x256, `ld_uncial20.btf` = лист 512x256; поля `.btf`:
  `'w'` = w*bpp (1024/2048), пара `(79,4)/(79,8)` = advance глифа 4 px / 8 px. Высота глифа у обоих
  одинакова (`uncial12` — тот же глиф с половинным advance), значит масштабать лист по сетке нельзя
  и `Size` на размер глифа не влияет.
- `[P]` Следствие: экранный текст = `C*s`, UI-контент = `k*s` → доля текста = `C/k`, т.е. в 16:9
  текст всегда в `1/k` крупнее ориентирa; при `k=1` (4:3 и 1280x960) = ориентир.
  Единственный рычаг — **сжать ink глифа внутри ячейки листа** (сетку не трогать), фактор = `k`
  динамически из `hd.cfg`; вертикальные метрики (`Leading/RowS/TextDX/TextDY`) масштабать тем же `k`
  (в `hd_scale` обёртки `SY()`/`SC()` уже есть).
- `[P]` Инструменты: `tools/pyc/install_patch.py` (`patches/<module>.py` → компиляция 2.2.3 → накат `.pyc`),
  `tools/archive/probes/probe_dlgshot.ps1`, `tools/archive/probes/measure_textrows.ps1` (параметры `-Png -X0 -Y0 -W -H -T -StepX`).
  Раскодированные листы шрифтов: `scratch_dir('ld')/font_ld_uncial12.png`, `scratch_dir('ld')/font_ld_uncial20.png`.
- `[P]` Незакрытый путь метрик (правится при правке шрифта): `ui.GetRealTextHeight(ptr, bbname)`
  читает движковые `ptr.GetFontSize`, `ptr.GetTextParams['RowS']` (движок отдаёт значения,
  уже умноженные на `k`) и использует их как канвас → коробки строк/тултипов в 16:9 короче в `k`
  раз, текст их переполняет (видно на снимке 4K: «Прокрутка карты в» + «Up» внахлёст).
  Обёртка в `hd_scale`: результат `/ HD_K`, при `k==1` identity. Метрику `GetFontSize` брать из
  `_orig_GetFontSize` (обёрнутый `BE.GetFontSize` уже делит на `k` — двойное деление ловится).
- `[P]` **Шрифт грузится НЕ из `data/textures`!** Каталог `data/fonts/` содержит
  `ld_uncial12.fdf`, `ld_uncial20.fdf` (текст) + движок читает лист по имени из `.fdf`
  (`ld_uncial20.tga` (утрачен: покрытия нет ни в git, ни в приватных архивах сессий Project/1-3.7z, 5.7z, 6.7z, 7.7z, original.7z, hd_pack.7z, python_libs.7z) = наш `.btf`). Формат `.fdf`: `name size sheet` (размер шрифта = pitch
  полосы листа: uncial12 = 25, uncial20 = 38), затем строки `char x y h` — позиция глифа в
  листе и его высота (ширина = до следующего x в полосе; адванс = пара `.btf` (79,4)/(79,8)).
  Полосы листа: y = 0, size, 2size... (6 полос uncial20, 9 у uncial12). Движок рисует глиф по
  таблице (`char x y h`), `SetFont(size)` на geometry не влияет — только метрики.
  Смена листа в `data/textures` без `.fdf` ломает индекс глифов (заголовки распадались
  фрагментами на снимке fnt71). Правильный сайдкар = пара `fdf + btf`.
- `[P]` **Схема генератора (рабочая)**: таблица `.fdf` остаётся оригинальной (позиции box
  `char x y h` не трогать — движок привязывает глиф к полосе листа по `y/size`, масштабирование
  `y` ломает индекс: заголовки распадались фрагментами на снимке fnt71b). Сжимается только ink
  внутри оригинального box: `nh = round(h*f)`, ink вставляется по `y' = y + (h - nh)` (низ box
  сохранён), ширина ink `round(w*f)` от левого края box. Фактор из пропорций: доля текста в 4K
  0.800, цель 0.567 → f = 0.71; измерение полосы заголовка (цель ~38 px при rect 67.5).
- `[P]` **Генератор листов глифов для 16:9** (`tools/archive/font_gen/rescale_font.py`). Разъединение листов по
  aspect: `hd_res.Prepare()` кладёт `config[game.root]/data/textures/ld_uncial12_169.btf` (файл установки)/`config[game.root]/data/textures/ld_uncial20_169.btf` (файл установки) (сжатые) в
  `ld_uncial12.btf`/`ld_uncial20.btf` при `w/h >= 1.6`, иначе оригиналы `config[game.root]/data/textures/ld_*_43.btf` (sidecar-пара в установке (создаёт пайплайн gen_font4x/pack_btf), в git не входит) (копии
  оригинальных `.btf`). Схема та же, что `mm_bkg01`. 2K и 4K дают `k = 0.75` — один статический
  набор закрывает обе цели; 4:3 (`k==1`) — оригиналы, обёртки identity.
  Генератор: декод листа (top-down RGBA), для каждой ячейки шириной `advance` (8 px uncial20,
  4 px uncial12) ink bbox по альфе (>32), сжатие фактором `f` с якорем **bottom-left** bbox
  (левый bearing и базовая линия сохраняются), вставка в ту же ячейку; сетка и адванс не тронуты.
  Runs глифов по вертикали масштабируются вместе с промежутками — структура runs листa не
  меняется (движок сегментирует глифы по колонкам advance). Фактор из пропорций: измеренная доля
  0.800 в 4K, цель 0.567 → `f = 0.567/0.800 = 0.708`, старт `f=0.71`, подгон по контрольному
  снимку (полоса заголовка цель ~38 px при rect 67.5).
  Утилиты: round-trip `.btf` проверен (decode32+build_blob = оригинал побитово), pack через
  шаблон оригинала (`pack_btf.pack_one`), PNG-мейкер минимальный (RGBA, filter 0).
  Инструменты: `tools/pyc/install_patch.py`, `tools/archive/probes/probe_shotwin.ps1` (съёмка окна живого процесса: поднимает
  topmost, снимает по GetWindowRect — снимки `probe_dlgshot` бывают перекрыты чужими окнами).


### Реальная линия текста: живые пути отрисовки и связь UV↔advance (перепроверка 2026-11-15, день)

Запись реестра опровержения — `docs/CONTRADICTIONS.md`, раздел «Перепроверка 2026-11-15 (день)».


- `[P]` **UI рисуется двумя живыми путями (оба через реальный OpenGL32):**
  - `0x470932` (glDrawElements, класс A, база [ecx+4], индексы edi, count ecx) —
    ВСЯ растровая графика UI (рамка диалога, иконки, кнопки, слайдеры). Сдвиг x на −100
    убирает рамку/иконки и НЕ трогает текст.
  - `0x477220` (glDrawArrays(mode,0,count), база [ecx+4], a0=первая вершина) —
    ВЕСЬ ТЕКСТ. Обнуление count → текст исчезает, графика остаётся; обнуление обоих
    путей → пустой серый экран.
  - Класс B (`0x4706e8`/`0x4707b7`, база [ecx+0x14]) в меню/диалоге НЕ вызывается (0).
- `[P]` **Текст строит `FUN_0041d020`** (вопреки старой записи «не срабатывает»):
  ~18.6k вызовов за 2.5 с при открытом диалоге (≈1 вызов на глиф на кадр), вызывает
  `0x471180`. Сигнатура: `ecx` = объект шрифта, аргументы `(float x, float y, char* text, …)`,
  `ret 0x14`. Разбор `.fdf` — `FUN_0041ce40`, UV — `FUN_0041cc90`.
- `[P]` Текст рисуется **в абсолютных канвас-координатах** (modelview в момент
  glDrawArrays = identity, проверено `glGetFloatv(GL_MODELVIEW_MATRIX)`); UV берутся из
  общего листа шрифта (`u,v` = 0.4..0.6 в примере), ширина UV-ректа = advance
  (u2−u1 = adv/texW): **геометрия и UV жёстко связаны через advance из таблицы `.fdf`**.
  Квад текста = ячейка `advance × pitch` (лог: x-шаг ≈10, y-высота 38 при uncial20).
- `[P]` Следствие для задачи «уменьшить текст при 4K»: рычаг ЕСТЬ и он на пути
  `0x477220` / `FUN_0041d020`. Ограничение движка: UV-ширина = advance, поэтому
  «апскейлить лист и рисовать мельче» требует расцепить UV и геометрию в эмиттере
  (внутри `FUN_0041d020`/`FUN_0041cc90`), иначе изменение advance кадрирует глиф.
  Именно эту связку обходил `tools/archive/font_gen/rescale_font4.py` сжатием ink в ячейке (отсюда потеря
  качества на 4K).
- `[P]` Таблица глифа в объекте шрифта: запись 20 байт, индекс = код символа,
  база `obj+0x5c`. Парсер `FUN_0041ce40` пишет `slot0`(=x)→`+0x5c`, `slot1`(=y)→`+0x60`,
  `slot4`(=advance)→`+0x6c`; `slot2`/`slot3` заполняет пост-обработка `FUN_0041db70`
  (`ecx = 0x51d530`, результат → `obj+0x44`). Рендер `FUN_0041d020` читает UV из
  `slot0..slot3`, а advance для пера — `fild [esi+0x10]`, шаг пера
  `0x41d3fb: fild [esp+0xf0]; fadd …; fstp [esp+0xe4]`. Это и есть точка расцепления
  «UV от ячейки / геометрия от advance» (план — `docs/archive/PATCH_PLAN_FONT.md`).
- `[P]` Состояние: EXE = baseline `45e93d46aad6ceb3dfc17e86d04e4f82` (не патчился).
  Новые инструменты: `tools/archive/frida_probe/ld_ver1.py` (дамп вершин), `tools/archive/frida_probe/ld_count2.py` (какие submit-пути живые),
  `tools/archive/frida_probe/ld_arr_test.py` + `scale_arr.js`/`no_restore.js` (мутация пути текста), `kill_path.js`
  (обнуление count — какой путь что рисует), `tools/archive/probes/shot_activate.ps1` (активация окна + снимок).

### Межбуквенный интервал не общий + замеры коэффициента A (2026-11-15, вечер)



- `[P]` **Межбуквенный интервал не общий для всего UI** (главная находка, из `HDINITBB` лога):
  `pitch=14 RowS=0` — 54 элемента (все строки диалога настроек), ошибки нет вообще;
  `pitch=14 RowS=-3` — блок описания персонажа в круге, +0.335 канвасной/символ;
  `pitch=29 RowS=-10` — заголовки («Настройки», «Ok», «Отмена»), наоборот −0.66/символ.
  Вывод: глобальный коэффициент нельзя применять «в лоб» без проверки — он двигает все три класса.
- `[P]` **Замеры (4K 3840x2160, `tools/measure/gyr2.py`, строка «Все свое искусство в магии»)**:
  4:3 `sd=108.22`, 4x без коэффициента `sd=110.32` (+1.94 %), 4x + `CORR=1.3384` **`sd=108.53`
  (+0.29 %)**, `cx=514.3` против 516.6. То есть коэффициент A = 0.3346 канвасной/символ снимает
  остаток точно. Цена: каждый квад уже на A (штрих на ~1.5–2 %), строки списка клавиш −5 units
  (−0.8 %) — они были +0.6 %, стали −0.2 % от 4:3.
- `[P]` 4:3-регрессия (1280x960, `scratch_dir('ld')/h43_dialog_nocursor.png` (снимок прогона) vs `scratch_dir('ld')/r43new_dialog_nocursor.png` (снимок прогона)):
  meanDelta=0.19, maxDelta=27, over_tol=12058 px — тот же уровень дизеринга/атмосферы, раскладка
  не поехала (k=1 → ветка identity, листы родные `*_43`).
