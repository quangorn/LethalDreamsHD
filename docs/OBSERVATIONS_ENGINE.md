## Геометрия и DPI (проверено замерами)
- `[P]` Система: desktop 3840x2160, системный масштаб DPI **75%**; `LETHALDREAMS.EXE`
  DPI-unaware, окно виртуализуется DWM: движок просит 1920x1440 → физический размер окна
  **1440x1080** (коэффициент 0.75). Снимки снимаются с `SetProcessDpiAwareness(2)`
  (как в `tools/archive/probes/probe_measure.ps1`) — тогда координаты снимка = физические пиксели.
- `[P]` `gamemodule.GetScreenSize()` в оконном режиме возвращает **размер desktop**
  (3840x2160), а НЕ размер рендера — в прогоне 1920x1440 вернул `[3840, 2160]`.
  Значит `k` нельзя считать из `GetScreenSize()`: источник — `hd.cfg`.
- `[P]` Движок отдаёт мышиные координаты в **канвас-единицах**: `m = физ_px / s`,
  `s = физ_ширина_окна / 1024`. Проверено по 6 точкам при окне 1440x1080
  (`s = 1.406`): OS abs (720,540) → движок сообщил (512,384);
  (1296,918) → (921,652); (144,108) → (102,76). Все шесть точек легли на `s = 1.406`.
- `[P]` Канвас = 1024x768 (подтверждает и `AutoPosition`, клампящий x≤1004, y≤748).
- `[P]` Масштаб движка: канвас-единицы умножаются на `s = w_окна/1024` (обе оси); при
  полном экране `s = 3840/1024 = 3.75`, физическое окно = весь экран, виртуализации нет.

Статический патч (exepatch12) — реализация; цепочка exe — `docs/PATCHES.md` и `docs/STATE.md`.

## Второе окно (видео/DirectShow) и альтернатива `h+1` (2026-11-16)

- `[P]` Эксперимент 2026-11-16 (scratch-сборка: `h+1` отключён в `patches/gamescript.py`,

### Краевой скролл оверленда: пороги `ui/olcamera` в канвасных единицах (17.11.2026)

- `[P]` Кто скроллит: `config[game.root]/data/scripts/ui/olcamera.pyc` (`OverlandCamera`).
  Обработчик `h_MouseMove` зарегистрирован на **сырое** движковое событие
  `WMO_MOUSEMOVE` (`globalscript.WMO_MOUSEMOVE = 10`), а НЕ на `WM_MOUSEMOVE` (= 11),
  который курсор релейтит после канвас-пересчёта. Значит `ms_lastx/ms_lasty` в
  `h_Update` = **движковые** координаты мыши, а не канвасные.
- `[P]` Условия краёв в `h_Update` (`decompiled_fixed/ui/olcamera.py`, строки 106..113):
  `x > screen_size[0]-1 = 1021`, `x == 0`, `y == 0`, `y > screen_size[1]-1 = 765`
  (`screen_size = [1024-2, 768-2] = [1022, 766]`) — **канвасные** числа, к движковым
  не пересчитаны.
- `[P]` Движковые диапазоны при `3840x2161 F=1` (`k=0.750347`, `s=w/1024=3.75`):
  X = `w/s` = 1024 (равно канвасной ширине), Y = `h/s` = `768*k` = 576. Поэтому
  верх (`y==0`), лево (`x==0`) и право (`x>1021`, движковый максимум 1023) достижимы,
  а **низ (`y>765`) недостижим никогда**: скролл вниз мышью не срабатывает ни при
  какой позиции мыши (движковый максимум 576 < 765). Симптом пользователя (17.11.2026):
  «вниз мышь у края экрана не скроллит, вверх/влево/вправо — работает; клавиша «вниз»
  работает».
- `[P]` Причина НЕ в `h+1`: при `h=2160` (`k=0.75`) порог тоже недостижим
  (`SY(765)=574 < 576 = h/s`), т.е. нижний скролл сломан во всех 16:9-конфигурациях
  с `F=1`; `h+1` (фикс мигания/OSD) на механизм не влияет и остаётся нужным.
  Отдельная причина для рамки `WS_BORDER` (2 px клиентa вне движковых `w,h`) — см.
  пункт выше.
- `[P]` Правка: порог низа = **движковая координата нижнего края канваса**,

### DirectShow-путь роликов (разбор `FUN_0049a1a0`, 16.11.2026)

- `[P]` Позиционирование видео-окна: `FUN_0049a1a0` (ролик) →
  `GetClientRect(0x51d5e8)` (это **само видео-окно**, а не главное) →
  `call *[edx+0x9c]` при VA `0x49a338`, аргументы `this=0x51d5f4`, `left=0`, `top=0`,

  стиль `0x46000000` (`WS_CHILD|WS_CLIPSIBLINGS`).
- `[P]` `4:3` считается из высоты: `width = 4*height/3`, `left = (client.right - width)/2`.
  Все целевые высоты (`2160/1440/1080`) делятся на 3, при 4:3-окне получается identity.

## Боевая камера: API, единицы и зум (18.11.2026)

- `[P]` Полный список методов камеры, доступных из Python (таблица `PyMethodDef` в
  `.data` `0x50f8a0..0x50f8dc`, 17 записей, terminator `0x50f8e0`): `CreateInnerData`,
  `DeleteInnerData`, `SetScene`, `LookAt`, `Move`, `Rotate`, `RotateAbs`, `MoveAlignedXZ`,
  `RotateAroundY`, `MoveY`, `GetPos`, `SetPos`, `SetOrtho`, `SetScale`, `SetMinHeight`,
  `GetDirection`, `GetDirectionAngle`. Имена лежат строками в `.rdata`
  (`MoveAlignedXZ` — `0x4ecc90`), С-функции — `0x410c70..0x4126b0`.
- `[P]` **`RotateAroundY` принимает РАДИАНЫ.** Замер: клавиша «turn_left» (`turn_speed`
  = 1.75 из `cfg_default.bcam`) за 0.9 с удержания повернула камеру на **90°**
  = 1.75·0.9 = 1.575 рад = 90.2° — сходится до десятых. `Rotate(0, -pitch, 0)` при этом
  работает в **градусах** (`cur_pitch` ∈ [-60, -45] из конфига).
- `[P]` **`SetOrtho(f)` разрушителен**: сбрасывает позицию камеры в `(0,0,0)` (замер:
  `pos=[76.7,12.6,128.5]` → `[-0.0,-0.0,-0.0]` сразу после вызова) — использовать нельзя.
- `[P]` **`SetScale(f)` — НЕ зум.** Формат `f` (строка формата `0x4ec81c`), функция
  `0x4125c0` умножает поля `camobj+0xf8/0x10c/0x13c` и на рендер боевой камеры не влияет:
  A/B-снимки при `scale=1.0` / `2.0` / `0.795` различаются только анимацией
  (HUD-зоны `mean=0.0000`, центр мира `mean=0.18`, `over8=2640/1266000`).
- `[P]` **Настоящий зум = высота камеры над землёй.** fov живёт в `camobj+0x144` (читает
  рендер мира `FUN_0049d630`, `0x49d74e`), из Python не меняется. Поэтому зум сделан как
  в оверленде (`olcamera.h_togglezoom_d`: 17↔62): каждый кадр камера держится на высоте
  `zoom_up` над землёй (`MoveY(camY - (zoom_up + GetIHeightInPosCamera(x,z)))`).
  Замер: `zoom_up` 8.25 → 6.5 (колесо вверх) и 6.5 → 15.5 → 24.5 → 33.5 (вниз);
  `cam.GetPos().y` 10.86 → 36.11; снимки подтверждают (персонаж ~180 px при 6.5 и ~40 px
  при 33.5 — обратно пропорционально высоте), UI не меняется.
- `[P]` **MMB приходит флагом в `WMO_MOUSEMOVE`**: `flags & globalscript.MK_MBUTTON` (16).
  Замер: `fl=16` при зажатой средней кнопке, `fl=0` после отпускания. SAME-событие, что
  и координаты (`B_Init` регистрирует `h_MouseMove` на `WMO_MOUSEMOVE` = 10).
- `[P]` **Колесо в бою**: `h_MouseWheel(x, y, btns, wheel)`, `wheel` = ±120 на щелчок
  (в логе три щелчка = `wheel=360`). До правки колесо крутило наклон (`is_pitch`) и
  сдвиг (`is_slide_ud`), теперь — зум.
