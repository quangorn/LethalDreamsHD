# PLAN_proxy_dll.md — план исследования: механизм прокси-DLL для патчей

**Статус: Фазы 0-бис–4 выполнены (18.11.2026); решение — EXE не трогаем,
`ldhook.pyd` — путь следующих правок; прокси `python22.dll` — резерв.**
Документ фиксирует исследование и план; числа,
помеченные `[P]`, измерены 18.11.2026 на текущей установке; проектные решения
помечены «предложение».

**Передача следующему агенту — `docs/archive/HANDOFF_ldhook.md`** (статус, что не
сделано, варианты дальнейших действий A–E, чек-лист перехода, грабли).

Цель — снять три ограничения текущего cave-патча EXE:

1. `.text` почти исчерпан: свободная зона `0x4ebf12..0x4ec000` = **238 байт**,
   занято **236** (`fixall.bin`), свободно **2 байта**.
2. Патчи пишутся на ассмблере (gas Intel) с ручной релокацией — неудобно и
   трудозатратно.
3. Нет логгеров и средств отладки: каждая ошибка = «собрал → запустил → снял →
   не то → переписал», падения без стектрейса.

## 1. Текущее состояние (измерено)

### 1.1 Свободное место в EXE

- `[P]` `LETHALDREAMS.EXE`: 4 секции, `.text` RVA `0x1000`, VirtualSize `0xeaf12`
  → конец `0xebf12` (VA `0x4ebf12` при базе `0x400000`).
- `[P]` `.text` кончается на `0x4ec000`; zero-run `0x4ebf12..0x4ec000` = **238 байт**.
- `[P]` `fixall.bin` = **236 байт** (`tools/exe/caves/fixall.s`), влезает с запасом 2 байта.
- `[P]` Других пригодных зон нет: int3-runs в `.text` ≤ 15 байт.
  Следствие: **добавить 4-ю правку в существующую пещеру нельзя** — нужен новый
  механизм доставки кода.

### 1.2 Что уже вшито (3 сайта `exepatch12`)

| сайт | VA | что делает |
|---|---|---|
| site1 | `0x41ce31` | масштаб листов/advance 4x-шрифтов |
| site2 | `0x40b494` | нормировка шрифта сразу в `SetFont` |
| site3 | `0x47dd80` | x-коэффициент world-проекции (16:9) |

Каждый сайт — `E9 rel32` + nop до конца сигнатуры (5 байт, как сейчас).

### 1.3 Свойства процесса (проверено)

- `[P]` EXE **не упакован**, **ASLR нет** (база `0x400000`), **DEP/NX нет**,
  **анти-отладки/самопроверки/CRC нет** (`docs/PATCHES.md`, разбор 2026-11-15).
- `[P]` Игра = C++ движок + встроенный Python 2.2 (магия `.pyc` `0xED2D`).
- `[P]` EXE статически импортирует: `KERNEL32` 102, `python22.dll` **53**,
  `USER32` 48, `ole32` 3, `GDI32` 2, `WINMM` 1, `ADVAPI32` 1, `DSOUND` 1.
- `[P]` `OpenGL32.dll` грузится **динамически** (`LoadLibraryA` + `GetProcAddress`,
  таблица указателей в heap) — статического импорта GL нет.
- `[P]` `lethaldreams.dll` **не импортируется и не загружается** (StarForce-стаб,
  удалён из установки 2026-11-18) — как носитель кода не годится.
- `[P]` Python-слой обязателен: `python22.dll` = финальный 2.2.3 (`4ee79da1…`),
  вся stdlib в `Lib/` собрана под 2.2.3.

### 2A. Альтернатива: `.pyd`-расширение, загружаемое игровым скриптом

Не cave и не прокси-DLL: код хуков — обычное C-расширение Python 2.2.3
(`ldhook.pyd`, экспорт `initldhook`), которое ставит хуки в памяти при загрузке.
Грузится не через import-таблицу EXE и не через подмену `python22.dll`, а **явным
вызовом из патчимого игрового скрипта**:

```python
import imp
imp.load_dynamic('ldhook', r'<путь к игре>/ldhook.pyd')
```

- `[P]` `imp.load_dynamic` — built-in Python 2.2.3 (проверено на `vendor/py223`).
  Он вызывает `LoadLibrary` + `initldhook` на C-уровне, минуя импортёр движка
  («реестр модулей»), поэтому не важно, умеет ли движок `.pyd`.
- `[P]` Почему не `sitecustomize.py`/`.pth` и не обычный `import ldhook`: движок
  **не исполняет тело `Lib/site.py`** при `Py_Initialize` (проверено —
  `docs/archive/RESEARCH_PY_DECOMPILE.md`, раздел «Проверено и НЕ работает»), а
  импорт stdlib ведёт по своему реестру. Единственный надёжный канал — явный
  `imp.load_dynamic`.
- Игровые скрипты (`ui/ui.pyc`, `ui/cursor.pyc`, …) — уже патчимые файлы
  (`patches/`, пайплайн `tools/pyc/pycbuild.py`); строка добавляется в текущий
  процесс сборки `.pyc`.
- Тайминг: грузить нужно из скрипта, исполняемого **до** первого вызова хукаемых
  функций (шрифты/проекция вызываются позже меню — подтвердить логом на спайке).
- Плюсы: EXE не трогаем; `python22.dll` не подменяем; 53 символа не форвардим;
  в установке один новый файл (`ldhook.pyd`) + правка уже патчимого `.pyc`.
- Минусы: `.pyd` обязан быть собран ровно под финальный 2.2.3 (есть в
  `vendor/py223`, `*.LIB`); крах `initldhook` ломает игровой скрипт (виден в
  логе, отлаживается); путь подтверждён спайком (Фаза 0-бис, 18.11.2026).

**Результат спайка (18.11.2026, Фаза 0-бис, гейт взят):** `imp.load_dynamic`
исполняется движком: игра из scratch-дерева (копия установки + `ldhook.pyd` +
`ui/ui.pyc` с блоком загрузки) стартовала, окно `LethalDreamsWndClass` 3840x2161
создано и держится (процесс жив), `initldhook` записал маркер
`ldhook_marker.txt` в каталоге EXE. Инструменты — `tools/ldhook/`
(`ldhook.c`, `fetch_headers.py`, `build.py`, `spike.py`, `probe_spike.ps1`).
Скриншот меню: GDI-захват отдавал устаревший кадр (сессия была заблокирована —
часы на кадре застыли на 16:20:12; AppCompat-флаг для scratch-пути добавлен,
окно 3840x2161), снимок повторить при активном дисплее.
Грабля found&fixed: `Py_InitModule(name, NULL)` в 2.2.3 падает
(`0xC0000005` в `python22.dll`, `Py_InitModule4` разыменовывает `methods` без
проверки NULL) — передавать пустую таблицу `{NULL, NULL, 0, NULL}`;
локальный репро — `vendor/py223/PYTHON.EXE -c "import imp; ..."`.

## 3. Прокси `python22.dll`: что известно и что учесть

### 3.1 Состав импортов (измерено, 53 символа)

- `[P]` **45 функций**: `Py_Initialize`, `Py_Finalize`, `PyRun_String`,
  `PyErr_Print`, `PyErr_Clear`, `PyErr_Occurred`, `PyObject_*`, `PyTuple_*`,
  `PyList_*`, `PyDict_*`, `PyString_*`, `PyInt_*`, `PyFloat_*`, `PyModule_*`,
  `PyImport_*`, `PyCFunction_New`, `Py_InitModule4`, `Py_FindMethod`,
  `PyCallable_Check`, `PyType_IsSubtype`, `PyFile_*`, `PySys_*`.
- `[P]` **8 data-экспортов** (не функции!): `PyInt_Type`, `PyFloat_Type`,
  `PyString_Type`, `PyTuple_Type`, `PyModule_Type`, `PyDict_Type`, `PyList_Type`,
  `_Py_NoneStruct`.
  Это принципиально: data-экспорты нельзя «прыгнуть» трамплином, их нужно либо
  форвардить (forwarder export), либо переопределять своими переменными,
  инициализируемыми из реальной DLL.
- `[P]` В установке **нет ни одного `.pyd`** (проверено: `*.pyd` в
  `config[game.root]` — пусто) → `python22.dll` импортирует только EXE, и
  прокси достаточно форвардить **53 символа**, а не все 753 экспорта DLL.
  Остальные DLL корня (`msvcr70`, `msvcp70`, `msvcr70d`, `BTexturer`) — проверить
  их import-таблицы в Фазе 0 (ожидание: `python22.dll` не импортируют).

### 3.2 Ограничение, которое нельзя нарушить

`python22.dll` — это **сам интерпретатор**, а не вспомогательная библиотека.
Прокси не должен менять семантику: stdlib `Lib/` и игровые `.pyc` собраны под
2.2.3 (магия `0xED2D`), альфа 2.2a4 их не читает (`docs/OBSERVATIONS_ENGINE.md`).

Следствие: реальная DLL должна остаться настоящим 2.2.3 и грузиться по-настоящему.

### 3.3 Предлагаемая схема

1. Реальную DLL переименовать: `python22.dll` → `python22_real.dll` (в установке).
2. На её место положить прокси `python22.dll`, который:
   - форвардит 45 функций: `EXPORTS Py_Initialize=python22_real.Py_Initialize` и т.д.;
   - форвардит 8 data-экспортов: `EXPORTS PyInt_Type=python22_real.PyInt_Type` и т.д.
     (PE-forwarder для data-экспортов — штатный механизм загрузчика: резолвит
     адрес переменной, не трамплин; риск низкий. Вариант Б — свои переменные,
     инициализируемые `GetModuleHandle`/`GetProcAddress` по реальному модулю, —
     остаётся резервом);
   - в `DllMain` (или в `Py_Initialize`-обёртке) ставит хуки и запускает логгер;
   - всю логику патчей держит на C.
3. Точки перехвата — **вариант А2 (предпочтительно)**: прокси в `DllMain`
   находит нужные места в `.text` сканом байтовых сигнатур (сигнатуры уже
   задокументированы) и ставит `E9 rel32` **в памяти**, через `VirtualProtect`.
   Тогда **EXE вообще не модифицируется** — md5-цепочка остаётся нетронутой,
   а `check_state` не видит изменений.
4. Вариант А1 (резерв): если сайт не находится сканом стабильно — ставить
   `E9 rel32` статически в EXE (как сейчас), но тело хука всё равно в DLL.

### 3.4 Что это даёт

- **Размер больше не ограничен**: 238 байт → любой объём кода в DLL.
- **Язык C**: компилятор сам считает смещения/релокации; исчезают ручные
  пересчёты x87-disp32 и rel32, которые сейчас делает `exepatch12.py`.
- **Отладка**: `OutputDebugString`, файловый лог, `printf`-подобный вывод,
  реальный отладчик (Visual Studio/WinDbg), а не «снимок после краша».
- **Безопасность 4:3**: те же guard'ы (`k==1` → identity) переносятся в C один в один.
- **Новые хуки без правки EXE** (вариант А2) — можно добавлять/убирать в рантайме.

### 3.5 Риски и как их снять

| риск | снятие |
|---|---|
| прокси ломает инициализацию Python | сначала сделать «чистый» прокси только с форвардингом, без хуков; проверить, что игра стартует и меню работает |
| data-экспорты не форвардятся | план Б: свои переменные + `GetProcAddress` по `python22_real` |
| сигнатурный скан не находит сайт | fallback на статический `E9` (вариант А1); сигнатуры уже проверены в `exepatch12.py` |
| d3d/окно/GL-путь не задет | хуки только на 3 известных сайта, остальное не трогаем |
| игра не стартует после подмены | откат тривиален: вернуть `python22.dll` из `backup_orig/`, удалить прокси |

## 5. Критерии перехода (когда игра стоит свеч)

Переходить, если выполнено **хотя бы одно**:

1. Нужна 4-я (или 5-я) правка движка, которая не влезает в 238 байт.
2. Логика правки перерастает «3–4 простых условия» (ветвления, циклы, таблицы).
3. Требуется частая отладка с логом/проверкой чисел на живой игре.

Не переходить, если: текущих 3 хуков достаточно и правки остаются мелкими —
тогда cave дешевле (не нужна подмена `python22.dll` и новый файл в установке).

**Вердикт 18.11.2026:** ни один критерий не выполнен → установка остаётся на
cave (`exepatch12`), `ldhook.pyd` — dev/следующий шаг (Фаза 4). Отладка
(logger, `OutputDebugString`, `stats`) при этом доступна уже сейчас на
baseline scratch-дереве, поэтому «переходить ради логов» не требуется.

- Не ставить хуки в произвольные места `.text` — только 3 задокументированных сайта
  (сигнатуры в `tools/exe/exepatch12.py`).
- Не забывать guard `k==1 → identity` — иначе 4:3 перестанет быть побитово прежним.
- Не коммитить бинарники игры: прокси-DLL и `python22_real.dll` — артефакты установки,
