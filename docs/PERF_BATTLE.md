# PERF_BATTLE.md — профилирование тормозов боя (18.11.2026)

Статус: `[P]` — измерено в сессии (frida-хуки + C#-семплеры, `tools/perf/`).
Установка игры не менялась (только чтение + внешние утилиты).

## Симптом

Бой с вражеским существом тормозит на любом разрешении (1920×1440 и
3840×2160), упирается в процессор; на оверленде нормально.

## Замеры (бой, главный поток)

- Процесс: **~100–105% одного ядра** постоянно (не GPU: GPU 3D 0–22%).
- Листья главного потока (sampler3, 30 с): exe-код — `FUN_0045ce80` (список)
  ~20%, `FUN_0047f800` (итератор) ~23%, `FUN_00434bc0` (дерево) ~5%,
  сисколлы — ~21% (`ZwQueryInformationThread`, `ZwYieldExecution`, `ZwSetEvent`,
  `ZwOpenKeyEx`).
- **Тяжёлый долгий вызов:** `FUN_0045e0a0` (VA 0x45e0a0) — цикл поиска цели:
  - норма: ~2 итерации, 0–1 мс;
  - патология: **до ~4400 итераций, 71–73 мс** (`perf_frida7.js`: `iterMax=4397`).
  - каждая итерация = `FUN_0045ce80` (полный скан списка `this+0x6c`, ~800
    элементов) + `FUN_0045dd70`/`FUN_0045c880`/`FUN_0045c5a0`/`FUN_0045c4b0`
    (все по отдельности 1–2 мс; heavy = сумма ~80 итераций).
- Цепочка: `FUN_0044bdd0` (боевое AI-обновление, ~33–46 вызовов/с) →
  `FUN_0045eee0` (движение/цель) → `FUN_0045e0a0` (поиск цели) → `FUN_0045ce80`
  (скан списка). ~85% времени боя — в этой цепочке.

## Что НЕ помогло

- `[P]` Троттлинг `FUN_0044bdd0` (skip каждого 2-го вызова, frida3): игра
  frame-rate-адаптивна — skip половины обновлений → вдвое больше кадров, CPU
  та же (реальные вызовы поделились на 2, среднее на вызов выросло в 2 раза).
- `[P]` Python-фильтр списка (B): список `this+0x6c` — не Python-овский
  (обход дал n=1 в лёгкой фазе; heavy-фаза — ~800 элементов, но список
  движковый, не из `mentality/std_brains.py`).

## План фикса (exe-патч, не реализован)

1. **Cap итераций** в `FUN_0045e0a0` (например, 32): heavy-вызов 71 мс → ~0.5 мс.
   - detour: back-edge `0x45e167: JNZ 0x45e117` (75 xx) → 5-байт JMP в cave;
     украденные байты (POP EBX и эпилог `0x45e169+`) переносятся в cave;
     cap → выход NULL (путь `0x45e1b6`, «не найдено» — вызывающий обрабатывает).
   - cave: `.rdata` trailing zero-run VA 0x50ec70 (912 B; нужен exec-флаг секции —
     как в exepatch_video43).
   - счётчик: `.data` zero-filled виртуальная область VA ~0x51d000+
     (WRITE+READ; raw .data 0x10f000+0xe000, virtual до ~0x16282c).
2. Валидация (frida8): cap `FUN_0045ce80` внутри `FUN_0045e0a0` (32 вызова →
   NULL) — ожидается падение `e0a0_max` с 71 мс до <2 мс при сохранении
   играбельности (цель переизбирается на следующем кадре).
3. Сборка по образцу exepatch12 (caves/*.s + build_cave.sh + патчер),
   scratch-прогон, снапшот, ярусы `--quick`/`--full`/`--untouched`,
   установка только с согласия пользователя.

## Обходные пути (без патча)

- `[P]` 1920×1440 не помогает (CPU-bound, не GPU).
- `[P]` троттлинг обновлений ineffective (frame-rate-адаптивность).
