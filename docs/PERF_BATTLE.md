# PERF_BATTLE.md — профилирование тормозов боя

Статус: `[P]` — измерено в сессии (frida-хуки + C#-семплеры, `tools/perf/`). Установка игры
не менялась (чтение + внешние утилиты).

## Симптом

Бой с вражеским существом тормозит на любом разрешении (1920×1440 и 3840×2160), упирается
в процессор; на оверленде нормально.

## Замеры (бой, главный поток)

- `[P]` Процесс: **~100–105% одного ядра** постоянно (не GPU: GPU 3D 0–22%).
- `[P]` Листья главного потока (sampler3, 30 с): `FUN_0045ce80` (скан списка) ~20%,
  `FUN_0047f800` (итератор) ~23%, `FUN_00434bc0` (дерево) ~5%, сисколлы ~21%
  (`ZwQueryInformationThread`, `ZwYieldExecution`, `ZwSetEvent`, `ZwOpenKeyEx`).
- `[P]` Тяжёлый долгий вызов `FUN_0045e0a0` (цикл поиска цели): норма ~2 итерации, 0–1 мс;
  патология — до ~4400 итераций и 71–73 мс. Каждая итерация = полный скан `FUN_0045ce80`
  (список `this+0x6c`, ~800 элементов) + `FUN_0045dd70`/`FUN_0045c880`/`FUN_0045c5a0`/`FUN_0045c4b0`
  (по 1–2 мс; heavy = сумма ~80 итераций).
- `[P]` Цепочка: `FUN_0044bdd0` (боевое AI-обновление, ~33–46 вызовов/с) → `FUN_0045eee0`
  (тик юнит-AI) → `FUN_0045e0a0` → `FUN_0045ce80`; ~85% времени боя — в этой цепочке.
- `[P]` Baseline тяжёлой фазы (бой у центра карты, `site5: window`): 77–136 вызовов/5 с,
  максимум 71 мс/вызов, `us_sum` = 50–98% ядра.

## Механика поиска цели

- `[P]` `FUN_0045ce80` — **один проход** по списку `this+0x6c`: фильтр `[obj+8] == arg`,
  из прошедших берётся минимум `[obj+0x24]` (целое, не расстояние). Возвращает объект или 0.
- `[P]` Расстояние в движке есть, но не в выборе кандидата: `FUN_0045c480` = `dx²+dy²`
  (координаты int в `+0x0c`/`+0x10`), используется в предикате `c880` (`cmp eax, [this+0x34]`);
  `c5a0` — таймаут, `c4b0` — копирование полей под маску (не предикат).
- `[P]` `FUN_0045c4b0` не мёртвый: маркирует `cur->filter` (`+0x08`) = 3 каждую итерацию;
  нормальная фаза native выходит `code=4` на итерации 2 (аудит байткода, скан и гейты 1:1).
- `[P]` Следствие: внешний цикл `e0a0` = до ~4400 **полных** проходов списка → O(итерации × n);
  лаги пропорциональны числу монстров и пикуют на смене агро (перебор целей).
- `[P]` Оба тяжёлых места читаемы в C++ и гейтятся офлайн: цикл `e0a0` (`battle/target.cpp`,
  Фаза 3) и пересчёт `45e1d0` (`battle/recompute.cpp`, решение 5.4); алгоритм — `docs/OBSERVATIONS_BATTLE_AI.md`.

## Что не помогло и обходные пути

- `[P]` Троттлинг `FUN_0044bdd0` (skip каждого 2-го вызова): игра frame-rate-адаптивна —
  skip половины обновлений даёт вдвое больше кадров, CPU тот же.
- `[P]` Python-фильтр списка: список `this+0x6c` — движковый, не из `mentality/std_brains.py`.
- `[P]` 1920×1440 не помогает (CPU-bound, не GPU).

## Кап итераций (19.11.2026 — снято)

- `[P]` Cap 32 в `FUN_0045e0a0` убирал лаги полностью, но **ломал агро** (31% поисков →
  «цель не найдена», монстры стоят): отсекается легальный перебор целей. В поставку не шёл;
  код и API сняты п. 3.4 плана (`site4`, env `LDHOOK_CAP`) — `docs/STATE.md`.
- `[P]` Однопроходный site6 в тех же условиях: максимум 25–36 мкс на вызов, `us_sum` ≤ 0.34% ядра —
  целевой поиск оптимизирован; остаток CPU боя создаёт другой нативный код (pathfinding/GUI).
- `[U]` Цель пересмотрена (19.11.2026): не оптимизация тормозов, а читаемый C++-порт боевой логики
  и pathfinding (fidelity-first, нативные листья допустимы) — границы, фазы и гейты
  в `docs/PLAN_BATTLE_AI_CPP.md`; прежний план — `docs/archive/PLAN_BATTLE_AI_PORT.md`.
