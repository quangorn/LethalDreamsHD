# Исследование: декомпилированные `.py` не работают в движке Lethal Dreams

**Актуализация (2026-11-14).** Механизм полной установки декомпилята (`install-all`, 434 `.pyc`)
оставлен: он ломает старт, а масштабные патчи прошлого агента рисуют меню криво. Игра восстановлена
к оригиналам, рабочая база = оригинальные `.pyc` + `python22.dll` 2.2.3. Текущий метод —
`pycbuild.py install-min` (только `gamescript.pyc` + генерируемый `hd_res.pyc`; чтение — генерируемый артефакт, в git не входит
одной строки `hd.cfg` и `SetDisplayMode`). Оригинальный `gamescript.pyc` НЕ зовёт
`SetDisplayMode`; шаблон `(1024, 768, 4, 0)` из `приватный архив сессий Project/1.7z, entry LethalDreams/_gs_min.py` (исторический скрипт (не в git)) — черновик, его нет в декомпиляте.
`hd.cfg` — одна строка (стартовый режим), меню настроек новые разрешения не показывать не умеет
(список строит движок, макс. 1280x960). Полный свод — `docs/INDEX.md`, раздел «Текущее состояние
(2026-11-14)». Текст ниже — историческое исследование, местами устарело.

Цель: понять, **почему исходники, восстановленные декомпилятором, движок исполняет, но UI не
строится**, и научить генератор выдавать `.py`, эквивалентные оригинальным `.pyc`.
Monkeypatch (`hdui.py` (утрачен: покрытия нет ни в git, ни в приватных архивах сессий Project/1-3.7z, 5.7z, 6.7z, 7.7z, original.7z, hd_pack.7z, python_libs.7z)) запрещён — нужен корректный `.py`.

## Объект

- Игра: `config[game.root]` (Lethal Dreams: The Circle Of Fate, 2003).
- Скрипты: `config[game.root]\data\scripts\**\*.pyc`, 434 файла. Магия `.pyc` =
  `0xED2D` = 60717 → серия Python 2.2.
- `python22.dll` оригинала содержит строку версии **`2.2a4+`** (альфа, copyright 2001),
  т.е. движок — не финальный 2.2, а ранняя альфа.

  `PyImport_ImportModule`, `PyRun_String`, `Py_InitModule4`, `Py_FindMethod`, `PyErr_Print`, …).
- Механизм `.py`: движок при `import` берёт `.py`, если он новее `.pyc`, и **пересоздаёт `.pyc`**

печатает через `PyErr_Print` туда, где мы её не видим (нет лога).

## Что нужно получить

1. **Точное место, где обрывается запуск** — текст Python-ошибки/трейсбек из движка.
2. **Эквивалентность байткода**: `.py` компилируется 2.2.3 → сравнить `dis` с оригинальным `.pyc`
   (тоже 2.2-байткод). Нас интересует первая функция, где байткод расходится.

## Проверено и НЕ работает: хук stdlib для перехвата вывода

Хуки, добавленные в модули стандартной библиотеки, **не исполняются** движком (проверено тремя
прогонми, логи пусты, игра при этом работает):

- хук логирования `sys.path`/`sys.version` appended в `config[game.root]scratch/rootpyc/site.py` (источник в git) —
  движок компилирует `scratch/rootpyc/site.py` (источник в git) (`scratch/rootpyc/site.pyc` (источник в git) создаётся во время прогона), лога нет;
- тот же хук в `config[game.root]\data\scripts\os.py` (файл новее vendored `os.pyc`) — лога нет;
- тот же хук в `config[game.root]\Lib\os.py` — лога нет.

Вывод: импорт stdlib идёт по механизму, который не берёт наши `.py` (скорее загрузка готовых
`.pyc` по реестру модулей движка), и `Py_Initialize` у движка не исполняет тело `scratch/rootpyc/site.py` (источник в git) как
обычный импорт. **Не трать время на stdlib-хуки для перехвата `PyErr_Print`.**

Надёжный канал перехвата Python-ошибок — только офлайн-сравнение байткода (Шаг 2) плюс, при
необходимости, собственный loader: движок компилирует `.py` для своих скриптов (`globalscript.py`,
`cfg/cfg_default.py` — проверено пересозданием `.pyc`), поэтому **текст ошибки можно получить,
оборачивая сами игровые скрипты** (`globalscript.py`, `ui/ui.py`, `ui/cursor.py`, `ui/mainmenu.py`,
`ui/bgui.py`): обёртка вида `try/except` + собственный форматированный трейсбек через
`sys.exc_info()` (модуль `traceback` недоступен движку, его `.pyc` нет) и запись в файл
абсолютным путём. Это единственный подтверждённый способ увидеть Python-ошибку движка.

## Найденная причина (подтверждена офлайн и live-прогоном)

**Причина серого экрана — артефакт декомпилятора, а не альфа-байткод.**
`uncompyle6` на Python 3 пишет байтовые литералы как `b'...'` (синтаксис Python 3.11+).
Python 2.2 такие литералы не парсит, и движок не может скомпилировать файл:

- `ui/bgui.py` — строка ~1585: `ks = {'A': …, b'\xc0': (vkeys.VK_A), b'\xc3': …}` (`IsHKPresent`);
- `sndchk.py` — `snd = b'...'` (cp1251-текст).

`ui/bgui.py` — каркас UI (`CreateControl`, `BGraphControl`), его импортируют `ui`, `mainmenu`,
`bpref`. Импорт обрывается на компиляции → движок не доходит до построения меню. Проверялось
`python2.7 -m py_compile` — 2.7 bytes-литералы принимает, поэтому дефект не был виден.

Гейт компиляции **локальным Python 2.2.3** (`pycbuild.py gate`) показывает: после нормализации
все 434 модуля компилируются, до нормализации падали 2 (`ui/bgui`, `sndchk`) плюс все файлы
ломались на module-level `return`.

### Нормализация `.py` (делает файл компилябельным)

1. вырезать заголовок uncompyle6 (строки `#` в начале);
2. вырезать module-level `return` (строка без отступа) — артефакт `RETURN_VALUE`;
3. `b'…'` → `'…'` (в Python 2 строка и есть bytes; эскейпы `\x..` сохраняют байты cp1251);
4. переводы строк LF: `compile()` у 2.2.3 падает на CRLF-исходнике (офлайн-гейт).

### Ключевой факт: офлайн-сборка `.pyc`

Магия `.pyc` локального Python 2.2.3 = `0xED2D` (60717) — та же, что у скриптов игры.
Значит `.pyc`, собранный офлайн этим интерпретатором, движок прочтёт, и компилятор движка
(2.2.3) идентичен нашему. Проверено live-прогоном: тело установленного `.pyc` совпадает
байт-в-байт с собранным (отличается только mtime в заголовке), т.е. движок load'ил наш файл
как есть, **без перекомпиляции**. Ставим `.pyc`, `.py` рядом не оставляем (иначе движок
перекомпилирует и свои SyntaxError печатает туда, где мы их не видим).

### Про паритет: 100% совпадения байткода не требуется

Движок — Python 2.2.3, наш компилятор — тот же Python 2.2.3, поэтому байткод нашего `.py`
автоматически совместим с движком. Оригинальные `.pyc` компилировались альфой `2.2a4+`, так
что полное совпадение байткода с оригиналом невозможно в принципе (разные peephole-оптимизации,
порядок констант, `-x` vs `UNARY_NEGATIVE`, отсутствие `__name__/__module__` в классе, разная
длина кода → jump-адреса). Паритет — **диагностика семантического дрейфа декомпиляции**, критерий
приемки: (1) компилируется 2.2.3, (2) паритет по операциям высокий и расхождения объяснимы
косметикой, (3) live-прогон: меню + отсутствие `0xFFFFFFFF`.
Замеренная близость (после нормализации): `ui/bgui_constant`, `ui/ui_macros`, `cfg/cfg_default` —
операции совпадают; `ui/gui_templates` 0.987, `ui/bgui` 0.995, `ui/ui` 0.988, `ui/cursor` 0.963,
`ui/mainmenu` 0.963. Остаток расхождений — порядок констант/`return`-хвосты/peephole.

### Третий дефект декомпиляции: целые-индексы внутри вложенных литералов

`uncompyle6` для байткода альфы `2.2a4+` местами пишет не значение константы, а её
**индекс в `co_consts`** — и там, где литерал лежит внутри вложенного литерала
(список внутри списка, dict внутри dict), этот индекс попадает в `.py` как **целое число**:

- `sounds.py`, декомпилят: `SoundGroups['Units']['GreenBird'] = {SOUND_DIR_KEY: '...', BIRTH: [[364, 410, 373, 428, 402]], ...}`
- оригинальный байткод: `LOAD_CONST 364` → `co_consts[364] = './data/sounds/ambient/objects/pain01.wav'`,
  `LOAD_CONST 410` → `'birth01.wav'`, `LOAD_CONST 373` → `'pain02.wav'` ...

Движок получает числа там, где ожидаются имена файлов → звук/юнит-таблицы не работают.
Дефект **не виден** паритетом, сравнивающим аргументы опкодов как индексы (`parity --strict`
на `sounds` показал «расхождение», которого нет: значения констант совпадают), и он не
ловится методом `reconstruct_literals` (тот работает для чистых литеральных
последовательностей, завершённых `STORE_NAME`/`STORE_ATTR`/`STORE_SUBSCR` с
**литеральным ключом**; внутри dict-литерала компилятор альфы делает
`BUILD_MAP 0; DUP_TOP; LOAD_CONST значение; ROT_TWO; LOAD_CONST ключ; STORE_SUBSCR`,
а ключевые `STORE_SUBSCR` у 2.2 имеют аргумент = индекс имени, не ключ).

Лечение (`pycbuild.py fixints`, воркер `litfix`):
1. воркер на 2.2.3 компилирует наш `.py` и печатает токены байткода A (оригинал) и B (наш
   компилят), где аргумент `LOAD_CONST` **разрешён к значению** (`LOAD_CONST HEX <repr>`),
   а в B дополнительно сохранён `SET_LINENO` как токен `SLINE <строка>`;
2. последовательности токенов выравниваются `difflib.SequenceMatcher`;
3. пара `(A = LOAD_CONST V, B = LOAD_CONST K)`, где `K` — целое и `co_consts[K] == V`,
   означает, что в исходнике написано число `K` вместо литерала `V`;
4. замена делается **по строке, указанной `SLINE` этого токена** (первое вхождение standalone
   числа `K`), причём заменяется только когда `V` — строка/список/кортеж/dict.

Последнее ограничение обязательно: числовые литералы декомпиллят воспроизводит верно, и без
него случаются ложные замены (`ui/ui`: `LOAD_CONST` со значением `1` совпал с индексом,
`co_consts[1] == 0`, и `return 0` превратилось в `return 1`). С этим_guard'ом `ui/ui` даёт
0 замен, `sounds` — 515, и `vdiff sounds` показывает лишь хвостовые `LOAD_CONST None /
RETURN_VALUE` (peephole, без semantics).

Порядок констант в альфа-байткоде важен: индекс `K` — это индекс именно в **оригинальном**
`co_consts`, поэтому `tree_consts()` обходит дерево кодовых объектов в том же порядке,
что и воркер.

## Гипотезы (по убыванию вероятности)1. **uncompyle6 реконструирует код под семантику финального 2.2, а байткод — альфы `2.2a4+`**:
   расхождение контроля потока (`while`/`if`/`try`/`for`), порядок `return`-артефактов, порядок
   statements в классе/модуле. Одна ошибка на уровне модуля → импорт `ui`/`mainmenu`
   прерывается (движок не печатает трейсбек нам) → меню не строится → серый экран.
2. **Порядок исполнения кода уровня модуля**: движок компилирует `.py` и исполняет; декомпилятор
   переставляет statements относительно оригинала (артефакты `return`, `del`, условия), что ломает
   инициализацию `dict = globalscript.GetDictionary()` и шаблоны.
3. **Разделение `/` в Python 2 (классическое деление)**: целочисленное деление даёт float;
   движок читает координаты через `PyInt_AsLong`. Оригинальные `.pyc` имеют идентичную семантику,
   поэтому это **не отличает** декомпилят — гипотеза вторична.
4. Различия `has_key`, augmented assignment, `map/filter`, строк/кодировки — маловероятны.

## Целевая геометрия (для финальной проверки)

Рендер = 3840x2160 (окно, desktop не меняется). UI-масштаб делает движок: `s = w/1024`, канвас
1024x768. Чтобы UI влезал по высоте и был крупным, движку надо передавать координаты
`k*c + dx`, `k = h*1024/(w*768) = 0.75`, `dx = (1024 - 1024k)/2 = 128` канвас-единиц
(полосы 480 px по бокам), `dy = 0`; мышиные координаты обратить: `c = (m - d)/k`.
Точки перехода в Python-слое: `ui.BActionElement.InitBillboard`, `SetPos`, `SetPrior`,
`AutoPosition`, `SetTextOffset` (значения для движка — целые, `int()`), обработчики мыши
`ui/cursor.py` (`h_MouseMove/LBDown/RBDown/LBUp/RBUp/Wheel/LDblClk`).
При 1920x1440 `k = 1`, `dx = 0` — ничего не меняется (штатный режим, пользователю подходит).
