# Handoff: масштабирование шрифтов UI в Lethal Dreams (4K / 2K)

Цель: текст в диалоге настроек (и весь UI-текст) при 3840x2160 и 2560x1440 должен иметь
**ту же пропорцию относительно интерфейса**, что в референсе 1280x960. 4:3 (`1280 960 32 0`)
должно остаться побитово оригинальным.

Рабочая папка: корень репозитория. Игра: `config[game.root]`.

## 2. Замерная база (единый протокол)

Замер: построчный профиль яркости `measure_textrows.ps1`, порог **T=170**, регион = canvas-rect
caption-поля, спроецированный на экран (`x*sx`, `y*sy`).

- Референс 4:3 (`scratch_dir('ld')/ref43_dialog_nocursor.png`), регион `(19,69)+588x38`:
  полоса **21 px** при экранном rect 37.5 px (canvas rect 30, sx=sy=1.25) → доля **0.56**.
- 4K fullscreen, родные листы (`scratch_dir('ld')/natk_dlg_nocursor.png` (снимок прогона)), регион `(56,155)+1763x113`:
  полоса **47 px** при экранном rect 84.4 px (canvas rect 30, `sy = 2160/768 = 2.8125`) → доля **0.557**.

**Вывод: вертикальная доля текста при 4K на родных шрифтах уже совпадает с референсом.**
Пропорцию ломает только горизонтальное растяжение: движок отображает канвас 1024x768 на окно
по осям (`sx = w/1024`, `sy = h/768`), поэтому глифы шире в `sx/sy = 3.75/2.8125 = 1.333` раза.

Компенсация: `k = sy/sx = h*1024/(w*768)`. При 3840x2160 = **0.75**, при 2560x1440 = **0.75**,
при 1280x960 = **1.0** (identity, 4:3 не трогается).

## 3. Что уже НЕ работает (dead ends — не повторять)

   глифы рассыпаются на фрагменты (снимки `f69k_*`, `f517k_*`). Генератор масштабает и таблицу

4. Frida ломает масштабирование меню (глиф «Изменить» уходит за нижний край) и при scan-сессиях

## 4. Модель рендера (декомпиляция, база EXE `0x400000`, ASLR нет)

- Парсер `.fdf`: `FUN_0041ce40` — пишет slot0=x, slot1=y, slot4=h (slot2/slot3 обнуляет).
  Caller: `FUN_0041d460`.
- Рендер строки: `FUN_0041d560(this, x, y, w?, ?, str, ?, ?, ?, lines, param)` — в начале
  `*(float*)(this+0x1460) = param_10`, `*(this+0x1464) = *(this+0x54)`, затем цикл строк и вызов
  `FUN_0041d020(this, x_line, y, str, param)`.
- Рендер глифов: `FUN_0041d020(this, x, y, str, advance?)`.slot-массив: `this + char*0x14 + 0x5c`
  (строд 0x14 = 5 int; `slot[0x10]` = advance, `x_next = x + slot[0x10]`).
  `pitch = *(int*)(this+0x40)`, `count = *(int*)(this+0x44)`, флаг `this+0x58`.
  Формируются 4 вершины (stride 0x20, записи пишут через `FUN_0040b210` в объекты
  `pvVar6+0/0x20/0x40/0x60`); константа `0xbf800000` (= -1.0f) и величина **`*(this+0x1464)`
  попадают в каждую вершину** — это масштабный рычаг (UV/геометрия глифа).
  `FUN_0040f840`, `FUN_00470d00(DAT_0051cc7c, 2, local_b8, 2)`, `FUN_00471180` — GL/объектные
  вызовы; `DAT_0051d490 + 0x2c` — текущий рисующий объект.

### Ключевой негативный факт

Счётчики Frida при **открытом** диалоге настроек в 4K:

```
FUN_0041d560 = 0   FUN_0041d020 = 0   FUN_0041d460 = 1   FUN_0041ce40 = 1
```

Т.е. родный EXE-глиф-рендер (`d560`/`d020`) при отрисовке UI-текста **не вызывается**; путь
загрузки шрифта (`d460`/`ce40`) один раз сработал. UI-текст рисуется другим кодом.

`BTexturer.dll` (102400 B, sha256 `93df6c06…`, база `0x10000000`) — **не рендерер**: импорты только
KERNEL32 (`FindFirstFileA`/`FindNextFileA`/`FindClose`), USER32 (`MessageBoxA`), MSVCP70; один
экспорт `TexturizeIt @ 0x100010c0`; имён GL нет; имена листов внутри `.btf` = `*.tga` → это
упаковщик листов в LDPACKER. Полностью декомпилана (515 процедур) в `scratch_dir('btx_decompiled')/`,
строк со шрифтами/GL там нет.

### GL-путь

- Ни EXE, ни `lethaldreams.dll`, ни `python22.dll` **не импортируют OpenGL**.
- Строка `"OpenGL32.dll"` (системная библиотека Windows, не файл проекта) в EXE на `0x4f2680`; рядом строки `OpenGl init failure. App will be
  terminated.` (`0x4ed868`), `OpenGL error 0x%Xh ( %s )` (`0x4efedc`), `Cannot find OpenGL`
  (`0x4f266c`). Есть таблица из 466 имён GL-функций (`glDrawRangeElementArrayATI` … );
  `glVertex2f` = строка `0x4f11e4`, `glBegin` = `0x4f2320`, `glTexCoord2f` = `0x4f148c`;
  xref на `glVertex2f` — один, `0x474ed6` (загрузчик).
- Хуки на 265 GL-экспорта модуля `opengl32.dll` (системная библиотека Windows, не файл проекта) (`base 0x693a0000`) — **счётчики 0**: движок
  вызывает GL через ICD-указатели (`wglGetProcAddress` → код `nvoglv32.dll` (системная библиотека Windows, не файл проекта), base `0x678c0000`),
  минуя stub-экспорты. Указатели в статических данных EXE (`0x400000..0x600000`) не найдены
  (`scanned=0`) — таблица указателей в heap. Экспорты `nvoglv32.dll` (системная библиотека Windows, не файл проекта) не имеют имён `gl*` →
  подписывать их надо по смещению (`base+off`).
- Сканирование heap на указатели в `nvoglv32` (для хуков GL с `returnAddress`) — рабочая схема,
  скрипты icd_attach.js / icdscan2.js — утрачены: покрытия нет ни в git, ни в приватных
  архивах сессий Project/1-3.7z, 5.7z, 6.7z, 7.7z, original.7z, hd_pack.7z, python_libs.7z;
  при attached-сессиях процесс часто умирает,
  сообщения `send()` теряются. Нужен лёгкий скан (ограничение range size, только нужные имена).

**Следующий практический шаг:** получить call-site GL-вызова, рисующего глифы (hook ICD-указателей
+ `this.returnAddress`), по адресу call-site найти функцию в EXE (база `0x400000`, `.text`
`0x401000..0x4ec000`), и патчить там масштаб по X на `k`. USER32-импорты EXE позволяют вызывать
`GetClientRect`/`GetSystemMetrics`/`FindWindowA`/`GetWindowLongA` из code cave — из них считается
`k = h*1024/(w*768)` (клиентское окно: 4K fullscreen и 2K → 0.75, 1280x960 окно → 1.0).

## 7. ВЫПОЛНЕНО (2026-11-14, вечер): сжатие листов — рабочий путь, бинарь не нужен

Задача закрыта **без патча EXE и без GL-хуков**: пропорция глифов компенсируется
листами шрифтов + таблицей `.fdf`. Пункт 1–2 раздела 6 (поиск GL call-site, бинарь)
не понадобился.

### Ключевое открытие: 4-е поле строки `.fdf` — АДВАНС, а не высота

Формат строки: `char x y adv`. `x` = левый край ячейки в листе, `y` = верх y-полосы
(кратно `pitch` из заголовка), `adv` = ширина ячейки/адванс в пикселях листа.
Проверено офлайн по всем родным листам: ink каждого глифа целиком лежит в
`[x, x+adv)`, шире адванса нет ни разу (552 глифа). Отсюда рендер: адванс берётся
из `.fdf`, и **его можно менять** — меняется и шаг строки, и ширина текста.

### Почему прежние попытки провалились (опровержение dead-end №1)

`rescale_font.py` / `rescale_font2.py` трактовали 4-е поле как **высоту**:
- `rescale_font.py`: `nh = h*f`, `ny = y + (h-nh)` → глифы уезжали вниз по полосе,
  индекс глифов в листе рвался → «расслоение на фрагменты»;
- `rescale_font2.py`: сжимал ink внутри ячейки, но **не трогал адванс**, а alpha
  ставил в `255` по факту покрытия → на антиалиасных глифах получались чёрные
  прямоугольники/жирные плашки.
Итог: обе «неудачи» — следствие неверной модели и alpha-бага, а не ограничения
движка. Сжатие ячейки (ink **вместе с адвансом**) работает.

### Рабочая модель

`k = sy/sx = h*1024/(w*768)` (0.75 для 16:9, 1.0 для 4:3) — та же, что в разделе 2.
Лист 32-bit, top-down; каждая ячейка `[x,x+adv) x [y,y+pitch)` перерисовывается в
`t = round(adv*k)` столбцов: RGB — взвешенное среднее по ink, **alpha — среднее
покрытие** (не 255). Лист и `.fdf` перепаковываются парой, адвансы в таблице = `t`,
позиции ячеек в полосе — последовательно слева, промежутки между ячейками тоже ×k.
Вертикаль не трогается.

## 8. ВЫПОЛНЕНО (2026-11-14, ночь): центрирование заголовков, межстрочный шаг, паддинг

Жалобы пользователя: (1) заголовок «Настройки» съезжает вправо; (2) на экране выбора
персонажа (`newgamemenu`) текст слишком высокий и без горизонтального паддинга,
вылезает за свиток и накрывает «Начать».

### 8.1. Движок фиксирует ширину текстовой раскладки при СОЗДАНИИ билборда

`SetText`/`SetFont` (в `InitBillboard`) раскладывают строки по текущей ширине rect;
последующий `Set(x,y,prior,w,h)` двигает/масштабирует бокс, но **не пересчитывает**
раскладку. Раньше `hd_scale.InitBillboard` вызывал `_orig_InitBillboard(InitParams)` с
канвасными w, а сжатый размер (`SC(w)`) ставил уже ПОСЛЕ — поэтому раскладка/центрирование
жили по исходной ширине: центрированный текст уезжал вправо (~+100 движк. ед. = «Настройки»),
блок текста заворачивался по неверной ширине (лишний «паддинг»/переносы).

**Фикс:** в `hd_scale.InitBillboard` движку сразу передаётся копия `InitParams` с
`EC/EY/SC/SY`, а в `Params` возвращаются каноничные канвасные `x/y/w/h` (bgui-раскладка
остаётся в канвасе). Проверка: центр заголовка «Настройки» 4K 2303 px → 1932 px (центр
экрана 1920); 2K 1290 (центр 1280); 4:3 640 (центр 640).

### 8.2. `SetFont(size)` НЕ масштабирует глифы — только метрику

Эксперимент `HD_FM=2` (вдвое больший аргумент `SetFont`) не изменил ни пикселя глифов.
Глифы рендерятся в НАТИВНОМ pitch шрифта; `GetFontSize()` возвращает именно pitch
(`ld_uncial20`=38, `ld_tahoma11`=19), независимо от `SetFont`. Движок рисует их
униформ-скейлом `s=w/1024`, поэтому в канвасе глиф выходит в `s/sy = 1/k` раз больше.

### 8.3. Межстрочный шаг = `GetFontSize() + RowS` — компенсация обязательна

Раньше `SetTextRowSpacing(SY(RowS))` масштабировал только дельту, а нативный pitch
оставался нетронутым → шаг в канвасе был в 1/k раз больше. Настройка:
`RowS_new = k*(pitch + RowS) - pitch` (`pitch = bb.GetFontSize()`). Тогда
`pitch + RowS_new = k*(pitch+RowS)` → канвасный шаг = `pitch+RowS` (как в 4:3).

Замер `newgamene` (Верumон), межстрочный шаг в канвасе:

| режим | до | после | эталон 4:3 |
|---|---|---|---|
| 3840×2160 | ≈24 | **16.0** | 16.0 |
| 2560×1440 | — | **16.0** | 16.0 |

Горизонтальный размах первой строки тела: 4K было 395 канвас (=весь бокс, наезд на
края), стало **368**; эталон 4:3 — 366. Текст снова вписан в свиток, «Начать» виден.

### 8.4. Регрессия

- 4:3 (`1280 960 32 0`): `imgdiff` со свежим эталоном — `maxDelta<=4`, 0 байт выше
  допуска → визуально побитово как было (шум дизеринга движка).
- 4K/2K диалог настроек: заголовок по центру, шаг строк корректный.

### Что осталось (не связано с этой правкой)

- В правой колонке настроек подписи клавиш наезжают на описание («…вправоLeft») —
  это `SetTextOffset`/ширина колонки, отдельная задача.
- Кнопка «Восстановить параметры по умолчанию» при 16:9 переносится на две строки.
